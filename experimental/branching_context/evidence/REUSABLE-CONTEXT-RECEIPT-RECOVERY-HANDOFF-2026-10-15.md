# Reusable-context receipt recovery follow-up

Context creation first writes a root branch receipt using a derived operation ID (`root-` plus the first 32 hex characters of SHA-256 over the client operation). The coordinator later durably publishes the numerical checkpoint with the original client operation ID. The durable publication appears in the authenticated presentation catalog as a `move` event with no presentation annotation. Treating the root fork as the client's durable acknowledgement was incorrect, and looking only for the original operation on a root presentation could not recover a lost final response.

The browser now confirms recovery only when the catalog contains the pending original operation and branch as a `move`, with `result.tip == result.root`, corroborated by a same-branch root fork presentation for that exact tip and namespace. A root fork alone leaves the operation pending. This reads canonical Store history and remains available after coordinator restart or subsequent branch movement; it does not rely on process-local `operation_status`.

The synthetic Chromium regression was red against the old predicate: `FAIL Error: context save consumed the question or retained saved files`. Its realistic fixture represented the hashed fork receipt and original-operation move separately. The real loopback HTTP/coordinator regression blocked publication after the root fork, verified no original-operation event existed yet, released publication, then confirmed the annotation-free move. It advanced the branch, restarted the fixture Store/coordinator, and confirmed the same historical durable move still identified the saved root without new model work.

Final checks on llm-60 passed: the serving verifier ran 126/126 with zero failures, errors, skips, or expected failures; G0 ran 51/51 with zero required real-backend cases; headless Chromium passed the context retry/recovery flow.
